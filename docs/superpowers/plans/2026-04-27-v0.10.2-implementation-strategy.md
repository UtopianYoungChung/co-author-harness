## 1. Problem statement

v0.10.1 closed two work items declared in v0.10.0's "Deferred to v0.10.1+" list (architecture/strategy doc mirrors for the four S4 binding decisions; SAFEGUARD Check 8 Sub-check H Register Appropriateness amendment) and shipped two `marketplace.json` hot-fixes. Its release notes §5 enumerate four items deferred to v0.10.2+:

2. Sub-check H `advisory_until: H_two_revision_cycles` flag retirement — provisional criterion: false-positive rate <30% across two revision cycles.
3. Quantitative thresholds for H positive markers — e.g., "≥1 concrete noun per 100 words"; "≥60% agent-subject sentences."
4. Pilot integration replay — clean-room replay on a fresh project (carryover from v0.10.0 RC).

The four items have **asymmetric workability** under a "kick off" framing. Item #1 is pure substrate work with no preconditions. Items #2 and #3 are empirically gated — #2 needs `h_advisory_cycles_observed >= 2` on at least one project plus the FPR criterion, and #3 is downstream of #2's flag retirement closing. Item #4 is a runtime task that requires identifying a pilot manuscript and running it through the full lifecycle ladder; "kicking off" means authoring the protocol, not executing the run.

This asymmetry forecloses a uniform "all-substrate" v0.10.2 sweep. The strategy adopted here is **mixed substrate-plus-setup**: ship substrate where preconditions are met (#1), ship telemetry/aggregator infrastructure plus plan docs where empirical observations are pending (#2, #3, #4), and let the empirical gates close on their own timescale post-v0.10.2 ship.

## 2. Theoretical framing — two-tier deliverable taxonomy

A v0.10.2 deliverable falls into one of two tiers:

- **Substrate** — binding contract changes (validator-gate-affected) plus code changes that ship logic the harness will execute. §9e H pre-filter is substrate. Calibration-log aggregator script is substrate (it ships executable Python). Telemetry field additions to existing artefact templates are substrate.
- **Forward-looking specification** — plan-doc-only artefacts that capture options, rationale, empirical preconditions, and adjudication templates for decisions that cannot bind without observations. Quantitative H thresholds are forward-looking specifications. The H flag retirement decision criterion table is a forward-looking specification. The pilot replay protocol is a forward-looking specification.

The taxonomy matters because the two tiers have different validator-gate semantics (substrate must pass the four-script gate; plan docs are gated only on path-hygiene), different RC-gate ceremonies (substrate touches RELEASE_NOTES §2.X enumeration; plan docs land as separate `docs/superpowers/plans/<date>-<title>.md` artefacts), and different §6.0 coupling-checklist applicability (substrate that edits a phase-runner Step triggers the four-row checklist; plan docs do not).

Authoritative trace (to be propagated into RELEASE_NOTES_v0.10.2.md §2): items #1 and #2's aggregator are substrate; item #2's plan doc is forward-looking; items #3 and #4 are forward-looking only.

## 3. Methodology — single-branch with per-item checkpoints

Per user adjudication 2026-04-27, v0.10.2 uses a **single `patch/v0.10.2` branch** off `main` (rather than the v0.10.0 multi-stage pattern of `stage/v0.10.0-S{N}` branches). Justification: the substrate surface is smaller than v0.10.0's snowball rollout (no new skill folders; no phase-runner Step edits; no schema bumps), and the forward-looking-spec items do not warrant per-stage binding semantic-review. Per-item checkpoints inside the single branch take the form of **annotated commit boundaries** (one or two commits per item), with the validator gate run between items as a continuity check.

Stage ordering is determined by surface invasiveness:

- Item #1 first (substrate; touches `references/DETERMINISTIC_CHECKS.md` and the overlay's pre-filter consumer point).
- Item #2 second (substrate aggregator script + plan doc; the script is small but new; the plan doc lands in `docs/superpowers/plans/`).
- Items #3 and #4 last (plan-doc-only; no validator surface).

The RC gate is a single ceremony at the branch tip: version bumps in `plugin.json` / `marketplace.json` / `README.md` / `CHANGELOG.md`; `RELEASE_NOTES_v0.10.2.md` authored; tag `v0.10.2` annotated; merge to `main` via `--no-ff`.

## 4. Per-item deliverables

### 4.1 Item #1 — DETERMINISTIC_CHECKS §9e H pre-filter (substrate)

**Goal.** Cheap counter probes that identify passages where Sub-check H is likely to fire, so the overlay can skip the full register-classification probe on passages with zero counter signal — reducing the H pass cost in expectation while preserving its full-fire correctness on detected risk.

**Three probes (mirroring the three H negative markers).**

- **Nominalisation density** — count of suffix-pattern matches `\w+(tion|ment|ance|ence|ity|ness|ing)\b` divided by total word count, against a configurable threshold (default 0.08; rationale: register-research literature places the 90th-percentile value around 0.10 for academic prose, so 0.08 fires above the median academic baseline without false-firing on technical-domain papers).
- **Prepositional-phrase stacking** — longest run of consecutive prepositional phrases identified by simple lookahead patterns (`\b(of|in|for|with|to|by|on|at|from|under|over|through|via)\s+\w+`); fires when run-length ≥3 (three consecutive of-phrases is the documented red flag in Williams' *Style*).
- **Hedging pile-up** — count of hedging-marker matches against the project glossary's hedge list (`research_notes/hedge_terms.md` or default list `[may, might, could, perhaps, possibly, likely, suggests, indicates, appears, seems, somewhat, relatively, generally, typically]`); fires when >2 hedges per 100 words.

**Output contract.** Each probe emits a per-passage tuple `(probe_name, raw_count, normalised_value, threshold, fired: bool)`. The pre-filter bundle (three tuples) is appended to the passage's overlay-input record. The overlay's H sub-check, on receiving the bundle, can short-circuit to NULL/CLEAN if all three `fired` values are `false` — saving the full register classification pass.

**Files modified.**
- `references/DETERMINISTIC_CHECKS.md` — new §9b "H pre-filter (counters; advisory-only)" with the three probes formally specified.
- `skills/accessibility-overlay/SKILL.md` — Sub-check H procedure step 1 reads the §9b pre-filter bundle if present; short-circuits as above; otherwise full classification.
- `skills/accessibility-overlay/references/sub_checks.md` — Sub-check H §6 procedure-amendment paragraph.
- `scripts/check8_h_prefilter.py` (new) — reference implementation of the three probes, callable as a CLI via `python scripts/check8_h_prefilter.py <manuscript_path>` for development and testing; used by the overlay only as a reference, not invoked at runtime by the overlay itself.

**§6.0 coupling-checklist applicability.** EXEMPT — no phase-runner Step edits; the overlay is not a phase-runner; §9b consumption point is internal to the overlay.

**Validator gate.** All four scripts must pass after the §9b commit. `scripts/check8_h_prefilter.py` is exercised manually during authoring; no new validator script is added (the four-script gate stays at four).

**Substrate — `scripts/aggregate_h_calibration.py`.**

## 7. Risk register

- **R-15 (v0.10.2-introduced) — Pre-filter / overlay coupling.** §9b ships counter probes consumed by the overlay's Sub-check H step 1. If a future overlay revision (post-v0.10.2) changes H's negative markers, §9b's three probes must move in lockstep. Mitigation: SAFEGUARD §H §6 step 1 pseudo-code names §9b explicitly; the §6.0 coupling-checklist row 4 (substrate-vs-advisory asymmetry) covers this if a future stage edits the overlay's Sub-check H sub-procedure.
- **R-16 (v0.10.2-introduced) — Pilot replay scope creep.** The pilot replay protocol (§4.4) names a metric set and exit criteria, but the actual run is a separate session. Risk: the replay session could expand to cover items beyond v0.10.0 snowball validation (e.g., introducing a Phase 4 reflector pass, exercising Sub-check H at full severity). Mitigation: protocol §7 explicitly enumerates known-deferred surfaces.
- **R-17 (v0.10.2-introduced) — Aggregator on inherited findings.** `aggregate_h_calibration.py` skips findings flagged `inherited_from_pre_h: true` per v0.10.1 grace-period spec. If the aggregator implementation incorrectly counts these as observations, FPR estimates will skew low (the grace period's MINOR-only verdict could appear as low FPR when in fact those findings were not subject to severity arithmetic). Mitigation: aggregator unit test on a synthetic fixture with mixed inherited/non-inherited findings.
