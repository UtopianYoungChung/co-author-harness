# Definitive Architectural Plan — co-author-harness-claude v0.11.0

> "The plugin needs to serve its purpose, and anything that does not add value to that purpose can be discarded."  — user, 2026-04-27.

## 0. Purpose re-anchor

The plugin's *only* purpose is to be a working harness for **PhD-level academic-writing review and revision**: a four-agent loop (Planner / Evaluator / Generator / Reflector) climbing the four-rung Lifecycle-Phase Ladder (Ph1 → Ph2 → Ph3 → Ph4) against a per-section ledger at `reviews/phase_state.json`, under the absolute grounding discipline of `references/GROUNDING_PROTOCOL.md`, producing reviewed and revised manuscripts that converge to a Manuscript Convergence Report (MCR) at Ph4 admission. Everything else in this substrate is either an *enabler* of that purpose (validators, calibration, snowball reference scaffolding, accessibility checks, named-scholar style overlays, the advisor MCP bridge) or *ornament* that should not survive a deletion-first audit.

This document binds the v0.11.0 release to that re-anchoring. It is not a wishlist; it is the cut criterion, the cut list, and the structural discipline that prevents recurrence. The predecessor audit at `reviews/promise_delivery_review_2026-04-27.md` named nine fixes against v0.10.2; this plan supersedes that list with a more aggressive scope and a structural anti-drift commitment.

## 1. Architectural principles

The plan is governed by five principles, in priority order. Where they conflict, the higher-numbered principle is the deeper commitment.

**Principle 1 — Purpose is the unique cut criterion.** A feature stays only if "without this, the four-agent loop on the Ph1→Ph4 ladder would produce materially worse PhD-tier review" is *yes*. Features that fail this test are not preserved on grounds of past investment, conceptual elegance, or near-completeness. Sunk cost is irrelevant; the substrate's job is to serve the writing purpose, not to monumentalise the maintainer's earlier reasoning.

**Principle 2 — Single source of truth (SSOT) for every fact stated more than once.** Version, skill count, command count, plugin name, plugin description, keyword list, deprecation flags. The SSOT for each is named exactly once and validated everywhere it appears. If a fact appears in two places without a validator linking them, the second appearance is a drift hazard and is either deleted or made derived.

**Principle 3 — Manifest is the sole authority for plugin identity.** `.claude-plugin/plugin.json` carries `name`, `version`, `description`, and `keywords`. No prose document asserts any of these in a form that could disagree. README, CHANGELOG, and marketplace.json either generate from or are validated against the manifest. The maintainer never edits the same fact in two places.

**Principle 4 — Documentation that requires memory to update is itself the drift hazard.** A "remember to bump the version trailer" affordance is the failure mode, not the fix. Where validators can replace memory, they do; where they cannot, the documentation is removed rather than maintained. Deletion is preferred over documentation; mechanical enforcement is preferred over deletion when it can be cheap.

**Principle 5 — Structural enforcement over rhetorical enforcement.** "NEVER use X" is a NEVER warning; a precondition check that refuses to dispatch when X is the failure mode is enforcement. Where the plugin currently has rhetoric, the plan upgrades to enforcement; where enforcement is too costly, the rhetoric stays but is named as such, and the maintainer accepts the residual risk explicitly.

## 3. Anti-drift architecture

The cuts of §2 reduce surface area; this section names the *structural* mechanisms that prevent the cut surface from re-growing through documentation slip. Each mechanism is named with its enforcement primitive — what file does the work, what failure mode does it prevent.

### 3.1 Manifest as the sole authority for plugin identity

`.claude-plugin/plugin.json` declares `name`, `version`, `description`, `keywords`. The remaining surface is *derived* or *validated*:

- **README's version mention** — currently `[![Version](...)](.claude-plugin/plugin.json)` shield. Stays as a shield (auto-fetches the manifest at render time); no prose version assertion.
- **README's "Skills (32)" hard count** — replace with "Skills (catalog)" linking to the catalog; let `catalog-check.py` validate the count against the directory. The count is derived, not asserted.
- **CHANGELOG.md** — top entry version is the manifest version. `version-check.py` already enforces this; preserved.
- **marketplace.json plugin-entry version** — must equal manifest version. `version-check.py` already enforces this (closed at v0.10.1); preserved.
- **No other prose document** asserts the version, the skill count, or the keyword list.

### 3.3 Validator extensions

The four maintainer scripts gain three new responsibilities:

**Extension to `version-check.py`.** New rule: `check_no_version_trailers_in_prose`. Greps every `.md` file under the plugin root *except* `CHANGELOG.md` and `docs/release-notes/RELEASE_NOTES_*.md` for a regex matching the trailer pattern (`\*Last updated: \d{4}-\d{2}-\d{2}`, `harness substrate at \*\*v\d+\.\d+\.\d+\*\*`, and the `(vX.Y.Z addendum)` pattern). Any match is BLOCKER. The check runs in `release-gate.sh` and is the structural enforcement of Principle 4.

**New script `manifest-coherence-check.py`.** Reads `.claude-plugin/plugin.json` and asserts:

- `description.length` ≤ 300 characters.
- `keywords.length` ≤ 12 entries.
- Every keyword matches a substrate marker (e.g., `snowball-references` → SK-33–36 must exist; `i-star` → SD/SR substrate must exist — which after §2.1 it does *not*, so the keyword is removed; the validator would have caught the v0.10.2 keyword-vs-substrate mismatch had it existed).
- `name` matches the directory name (`co-author-harness-claude` ↔ plugin root tail).

**Extension to `catalog-check.py`.** New rule: `check_README_skill_count_is_derived_not_asserted`. Greps README for any `\bSkills \(\d+\)` or `\b\d+ skills\b` pattern; BLOCKER on assertion. README must use `Skills (catalog)` or similar non-numeric form. The skill count is exclusively derived from `ls skills/` by the validator.

**Extension to `path-hygiene-check.py`.** New rule: `check_no_orphan_directory_references_in_README`. Greps the README repository-layout table for directory references (`legacy/`, `releases/`, `models/`, etc.); BLOCKER on any referenced directory that does not exist on disk. Closes the §2.3 class of slip permanently.

### 3.4 Single-source-of-truth registry for repeated facts

A new file `.claude-plugin/ssot.yaml` declares the SSOT for every fact stated more than once:

```yaml
plugin_identity:
  authority: .claude-plugin/plugin.json
  consumers:
    - README.md (badge shield only; no prose assertion)
    - CHANGELOG.md (version trailer per release)
    - .claude-plugin/marketplace.json (plugin-entry version)
skill_count:
  authority: ls skills/ | wc -l
  consumers:
    - README.md (catalog link, no number)
    - skills/plugin-commands/SKILL.md (catalog table — derived at edit time)
command_count:
  authority: ls commands/ | wc -l
  consumers:
    - skills/plugin-commands/SKILL.md (manual script commands subsection)
deprecation_flags:
  authority: per-skill SKILL.md frontmatter `deprecated: bool`
  consumers:
    - SKILL_REGISTRY.md (deprecation column)
    - plugin-commands routing table
phase_ladder_definitions:
  authority: references/PHASE_PROTOCOL.md
  consumers:
    - all agents/*.md (read-only references)
    - all skills/run-phase-*/SKILL.md (read-only references)
grounding_rules:
  authority: references/GROUNDING_PROTOCOL.md
  consumers: every agent prompt (read-only references)
external_verifier_classes:
  authority: references/EXTERNAL_VERIFIERS.md §1.5
  consumers:
    - GROUNDING_PROTOCOL.md Rule 7a (cross-reference)
    - skills/seed-snowball-discovery/SKILL.md (Class 1 fall-through)
```

The file is read by a new validator `ssot-check.py` that asserts every consumer's claim about a fact agrees with the authority. The validator is the *structural* enforcement of Principle 2; documentation that drifts from its SSOT fails the gate.

The smoketest does *not* assert prose quality (that is a judgment, not a measurement); it asserts *contract fulfilment*. The fixture runs in `release-gate.sh` as the final gate. Implementation cost: ≈4–8 hours, one session; closes the operational delivery gap permanently.

### 3.6 Deletion-over-documentation at every prose surface

The plan applies Principle 4 surgically: every `**when X**` conditional clause across the substrate is a candidate for either (a) deletion (if X is being cut) or (b) precondition-check (if X is operationally important). Examples:

- `**when `sd_sr_required: true`**` clauses — deleted under §2.1.
- `**when `wiki_linked: true`**` clauses — *not* deleted; instead, the precondition is enforced at the skill-entry point (e.g., `seed-snowball-discovery` SKILL.md Phase 0 already encodes this; preserve).
- `**NEVER skip `/classify-manuscript`**` warnings in `plugin-commands` — *upgraded* to a precondition check in `pre_phase_advance_check.py`: refuse to advance Ph1 → Ph2 if `reviews/classification.md` is absent.

The general pattern: turn "remember to do X" into "validator BLOCKERs if X is missing."

## 6. What the plan does not do

For honesty: the plan does not promise the plugin will produce better PhD-tier review than v0.10.2. It promises the plugin will *credibly claim to* — that the gap between manifest promise and substrate delivery will be closed, the gap between documented capability and operational invocation will be measured, and the recurrence of either gap will be made structurally costly. The deeper promise — that the four-agent loop, when invoked with discipline by a Claude session against a real manuscript, produces a review a journal reviewer would call PhD-tier — remains an empirical claim contingent on the user's discipline and the model's capability. No architectural plan can substitute for that.

What the plan does do is remove the conditions under which the maintainer's *worry* is grounded in the substrate. After v0.11.0, the worry becomes either (a) a worry about model capability (which is not a plugin-substrate problem) or (b) a worry about user discipline (which the substrate can scaffold but not enforce). Both are honest worries the maintainer can name and address directly. The current worry — that the plugin's manifest, README, governance trailers, and substrate disagree about what the plugin even is — is the worry the plan retires.
