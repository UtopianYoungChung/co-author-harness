# AI harness (concept note)

To understand **Harness Engineering** in the context of AI—and specifically for a tool like **Claude Code**—you first have to shift your perspective from "Prompt Engineering" to "Systems Engineering."

While prompt engineering focuses on the *input* to the model, **Harness Engineering** focuses on the *environment* in which the model operates. It is the construction of the scaffolding, safety rails, and feedback loops that allow an AI agent to interact with a real-world system (like a codebase) without causing chaos.

Here is a detailed breakdown of harness engineering as it relates to Claude Code.

---

### 1. The Concept: What is an AI Harness?
In traditional software testing, a "test harness" is a collection of software and test data configured to test a unit of code. 

In **Agentic AI (like Claude Code)**, the harness is the infrastructure that mediates between the LLM's reasoning and the computer's execution. Because Claude Code can read files, write code, and execute shell commands, it cannot simply be "sent a prompt." It needs a harness to:
*   **Provide Context:** Feeding the right files into the window.
*   **Execute Actions:** Translating "I want to fix the bug" into `git checkout -b fix-bug` and `npm test`.
*   **Capture Observation:** Feeding the error message from the terminal back into the model.

### 2. Key Pillars of Harness Engineering for Claude Code

#### A. The Execution Environment (Sandboxing)
One of the primary jobs of a harness engineer is ensuring the agent doesn't destroy the host system.
*   **Containerization:** Running Claude Code inside a Docker container or a VM so that if it accidentally runs `rm -rf /`, it only kills a disposable environment.
*   **Permission Layers:** Implementing "Human-in-the-Loop" (HITL) checkpoints. Claude Code asks for permission before executing "dangerous" commands (like writing to a file or running a script).
*   **Resource Limits:** Capping CPU and RAM usage so an infinite loop generated by the AI doesn't crash the machine.

#### B. The Tooling Interface (MCP & APIs)
Claude Code relies on the ability to "call tools." Harness engineering involves defining these tools clearly.
*   **Model Context Protocol (MCP):** Anthropic uses MCP to standardize how the agent connects to data sources (Slack, GitHub, Local Files). The "harness" here is the implementation of these servers.
*   **Tool Definition:** Ensuring the tool descriptions are mathematically precise so the model knows exactly when to use `grep` versus `ls`.

#### C. The Observation Loop (The "Feedback" Harness)
A raw LLM is a feed-forward system. An agent is a loop. The harness manages the **Reasoning $\rightarrow$ Action $\rightarrow$ Observation $\rightarrow$ Reasoning** cycle.
*   **State Management:** Tracking what the agent has already tried so it doesn't get stuck in a loop (e.g., trying the same failing command five times).
*   **Telemetry:** Logging every tool call and response to analyze where the agent "hallucinated" a file path or failed to understand a compiler error.

#### D. Evaluation Harnesses (Eval Sets)
How do you know if a Claude Code update made the agent better or worse at fixing bugs? You build an **Eval Harness**.
*   **Golden Sets:** A collection of 100 known bugs and their correct fixes.
*   **Automated Benchmarking:** The harness automatically runs Claude Code against these 100 bugs and checks if the resulting code passes the unit tests.
*   **Regression Testing:** Ensuring that fixing one agent behavior doesn't break another.

### 3. Applying this to your Workflow
If you are using Claude Code and want to apply "harness engineering" principles to your own development, you should focus on:

1.  **Environment Isolation:** Don't run agentic tools on your primary OS; use a DevContainer or a cloud IDE (like GitHub Codespaces).
2.  **Test-Driven Agentics:** Instead of telling Claude "Fix the bug," provide a failing test case. The **test suite becomes the harness** that tells the AI when it has succeeded.
3.  **Context Pruning:** Don't give the agent the whole repo. Use `.gitignore` or specific file inclusions to limit the "noise" the agent has to process.

### Summary Table

| Feature          | Prompt Engineering                       | Harness Engineering                       |
| :--------------- | :--------------------------------------- | :---------------------------------------- |
| **Focus**        | The wording of the request               | The environment of the execution          |
| **Goal**         | Better output text                       | Reliable system state change              |
| **Mechanism**    | Personas, Few-shotting, Chain-of-Thought | Docker, MCP, Eval Sets, Shell integration |
| **Failure Mode** | Hallucination of facts                   | Execution of destructive commands         |
| **Metric**       | Perceived quality of answer              | % of tasks completed successfully         |
