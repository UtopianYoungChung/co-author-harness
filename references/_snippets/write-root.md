**Write root (binding, one rule).** Every project-relative path a role, skill or script writes (for example `reviews/revision_plan.md`, `reviews/*_findings.md`, `reviews/convergence_log.md`, `reviews/convergence_journal.jsonl`, `reviews/reflection_report.md`, `reviews/escalation_log.md`, `reviews/snowball_log.md`, `reviews/external_verification_log.md`, `reviews/graph_overlay_*.md`, `research_notes/lessons_learned.md`, `research_notes/directives.md`, `references/REFERENCES.md`, `milestones/*.md`, `manuscript/revision_log.md`) is relative to the **write root**, not to the project root:

| Project | Write root |
|---|---|
| Governed Workbench package (`<governed-root>/research/60_Workbench/<work-id>/`) | the active shipment lane `reviews/harness/shipments/<shipment-id>/` |
| Any other project | the project root (unchanged) |

Resolve it with `python <package-root>/scripts/output_lane.py <project_root> [--shipment-id ID]` (or `output_lane.resolve_write_root`); `<package-root>` is `${CLAUDE_PLUGIN_ROOT}` on Claude hosts, otherwise the installed package directory containing `version.json`. The path `reviews/revision_plan.md` in a governed package is therefore `<package>/reviews/harness/shipments/<shipment-id>/reviews/revision_plan.md`.

- **Shipment id.** In a governed package the Planner runs `python <package-root>/scripts/output_lane.py set-active --project-root <package> --shipment-id <id>` once at run start. It records the id in the pointer `reviews/.harness/active_shipment.json` (through the destination guard) and creates the lane. Scripts and hooks resolve the id in this order: explicit argument (`--shipment-id`), environment `COAUTHOR_SHIPMENT_ID`, then the pointer; an explicit argument or environment value that disagrees with the pointer wins. A missing id or a malformed pointer fails closed: name the id, do not fall back to the package path. `set-active` refuses a non-governed root.
- **Never redirected.** `reviews/phase_state.json` (lifecycle state, written only by its canonical transaction), anything under `reviews/.harness/` (tool control plane), and the re-pin files `reviews/repin_rebind_request.json`, `reviews/repin_rebind_request.<epoch>.applied.json`, `reviews/repin_rebind_request.<epoch>.stale.json`. Their paths stay at the project root.
- **Reads.** A seat-produced file listed above (findings, reports, logs, plans, signoffs) is read from the lane only. Package-native sources (manuscript, accepted `references/REFERENCES.md`, effective `research_notes/directives.md`, ledger-bound milestone artifacts) are read where the package keeps them; a seat-written copy in the lane is a proposal, not the accepted source. A seat extending its own pending proposal in this shipment (a `references/REFERENCES.md` delta, lessons) also reads its lane copy so it does not repeat entries already proposed.
- **Recorded paths.** A path recorded inside an artifact as a binding (an F1 `reader_accessibility_policy` path or `grounding_basis` entry, an M5 terminal binding, a ledger-recorded evidence path) is relative to the package root, not the write root. For a lane file it therefore carries the lane prefix, for example `reviews/harness/shipments/<shipment-id>/reviews/deterministic_c1.md`.
- **Legacy lane.** `reviews/.harness/shipments/<shipment-id>/` is recognised by the destination guard so that an existing legacy shipment can be continued by hand; scripts write only to the current lane.
- **Nothing else.** Writes outside the write root, the never-redirected paths and `outputs/co-author-harness/staging/` are refused by `scripts/destination_capability.py`; the shipment lane implies no acceptance, registration, promotion or authoritative-state update.
