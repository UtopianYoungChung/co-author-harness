# Architecture Review — v0.8.0 Upgrade Architecture (r18)

## 1. Executive summary

The architecture document is structurally sound. The eight-phase authoring sequence, the five-layer decomposition, the single release-gate, and the four soundness gates (SG-1 through SG-4) form a coherent plan. Phases 0, 1, and P2.1–P2.7 are closed with grounded verification evidence. The next entry point (P2.8, A-GK-4 scope-freeze) is correctly identified and its preconditions are met on the wip0 substrate.

This review surfaces **seven findings** organized by severity. None blocks P2.8 entry. Two should be addressed before Phase 3 begins; the remainder are Phase 5 substrate-cleanup scope.

## 2. Release-gate delta (r18 claim vs. live audit)

**r18 claims:** 1 blocker, 8 warnings.
**Live audit (2026-04-22):** 2 blockers, 8 warnings.

The new blocker is: `[BLOCKER] plugin.json.description (602) > peer max (284)`. The wip0 `plugin.json` description field (602 chars) exceeds the peer-max ceiling (284 chars) established by the release-gate's manifest-length check. This was not present in the r18 verification because the description was widened during the P2.1–P2.7 authoring sessions (the v0.8.0 β framing was added to the description at some point during sub-phase closures).

**Severity: MINOR (Phase 5.2 scope).** The description must be trimmed at Phase 5.2 when the version-bump lands. The existing r18 plan already calls for a description rewrite at P5.2 — "Update the plugin description to reflect the Ph3/Ph4 redesign." This finding widens the existing P5.2 scope by requiring the rewrite to also respect the 284-char ceiling. Not a structural risk; the description is the last thing written before zip build.

**Recommendation:** Amend §3.2 Phase 5.2 to note the peer-max constraint (`plugin.json.description ≤ 284 chars`), so the Phase 5 author does not re-discover it.

## 4. Structural findings

### F-1. `AGENT_ORCHESTRATION.md` carries 40+ stale Tier-vocabulary strings

`references/AGENT_ORCHESTRATION.md` contains ~40 instances of `current_tier`, `last_approved_tier`, `tier_entry_log`, `t1_pstage_declaration`, `t3_last_activity_at`, `T3_converged`, `T4_ready`, and `tier_state.json`. These are concentrated in the v0.7.0 §§8.2a/8.2b body-prose blocks that describe the historical schema shape.

**Risk:** Low. `AGENT_ORCHESTRATION.md` was not a Phase 2 target (Phase 2 rewrote `PHASE_PROTOCOL.md`, agent prompts, skills, and `AGENT_CONTRACTS.md`). The stale vocabulary is in documentary/historical sections, not normative dispatch instructions. However, an agent reading the file at runtime will encounter `current_tier` and `tier_state.json` as if they are live — this is a latent confusion source.

**Recommendation:** Schedule a vocabulary sweep of `AGENT_ORCHESTRATION.md` as Phase 5 hygiene. The sweep should distinguish between (a) provenance/rename-chain paragraphs (preserve with a documentary note) and (b) procedural paragraphs that should read Phase vocabulary (rewrite). This is the same pattern as Phase 3.4's `agents/evaluator.md` cleanup, but for the orchestration reference.

### F-2. `pre_tier_advance_check.py` → `pre_phase_advance_check.py` rename not scheduled

The wip0 substrate ships `scripts/pre_tier_advance_check.py` (legacy filename). Multiple v0.8.0-authored governance documents — `phase_state_schema.md`, `PHASE_PROTOCOL.md`, `AGENT_CONTRACTS.md`, `run-phase-1/SKILL.md`, `run-phase-2/SKILL.md`, `phase_notifications.yaml` — reference `pre_phase_advance_check.py` as if it exists. `phase_state_schema.md §7` explicitly notes: *"the companion script may ship under the legacy `pre_tier_advance_check.py` filename as a forwarding shim; consumers should migrate to the phase-named path before v0.7.5 RC."*

The v0.8.0 upgrade architecture §3.2 does not schedule this rename in any phase. Phase 0 covered the `tier_state_schema.md → phase_state_schema.md` rename but not this script. Phase 3.4 covers `agents/evaluator.md` Tier → Phase vocabulary but not script filenames.

**Risk:** Medium. The script is referenced by name in the governance docs. If a consumer project or automation calls `pre_phase_advance_check.py`, it will fail with "file not found." The documents promise the rename "before v0.7.5 RC" — v0.8.0 absorbs v0.7.5 RC, so the promise is due now.

**Recommendation:** Add a Phase 5 sub-step (or a Phase 3 adjunct) that performs a `git mv scripts/pre_tier_advance_check.py scripts/pre_phase_advance_check.py` and updates the py_compile list in `release-gate.sh`. Alternatively, create a shim at the phase-named path that imports from the legacy name. The architecture document should acknowledge this gap.

### F-3. `AGENT_ORCHESTRATION.md` describes 15-field `SectionStateObject` (v0.7.0 shape); v0.8.0 is 16 fields

`AGENT_ORCHESTRATION.md` §8.2a (line ~454) describes the `sections` object with "fifteen canonical fields enumerated in `phase_state_schema.md §6.2`" using v0.7.0 field names (`current_tier`, `last_approved_tier`, `tier_entry_log`, etc.). The v0.8.0 substrate has widened to 16 fields and uses Phase vocabulary.

**Risk:** Low (same class as F-1). Documentary staleness, not a normative conflict — the schema doc and the validator are authoritative. But a fresh agent reading `AGENT_ORCHESTRATION.md` will get an incorrect field count and vocabulary.

**Recommendation:** Fold into the F-1 vocabulary sweep at Phase 5.

### F-4. Falsification table readiness for P2.8

The eleven-row stub at `v0.7.5_phase3_refinement_loop_proposal.md §3.P-9.1` is well-structured. Each row has: check name, anticipated edit class (sub-arg 1 stub), anticipated refine-side coverage (sub-arg 2 stub), and a "TBD at RC freeze" disposition column. Row 11 carries a prior constraint (documented at the row-level asymmetry paragraph) restricting its disposition to two of the four outcomes.

**Pre-conditions for P2.8 execution:**

1. The four disposition outcomes are clearly defined (lines 126–129 of the proposal) — **met**.
2. Row 11's constrained disposition set is documented (line 133) — **met**.
3. The instrumentation hook (classification-stability metric, 80%/60% thresholds) is specified (line 151) — **met**.
4. The filing discipline (A-GK-4) is specified (line 149) — **met**.
5. The user understands that each disposition is binding and amends the Ph3-refine profile surface — **this is the P2.8 session itself**.

**One observation:** The architecture (§3.2 Phase 2.8) says "Populate the disposition column of the §3.P-9.1 eleven-row falsification table **under user review**" and "Decision surface is binding before Phase 3 begins." However, the architecture does not specify *where* the populated table is recorded. Options: (a) amend the table in-place in `v0.7.5_phase3_refinement_loop_proposal.md`, (b) create a separate disposition artefact at `proposals/v0.8.0_falsification_table_dispositions.md`, or (c) inline the populated table into the architecture document itself. The source proposal's filing discipline (line 149) says "filed in place in this §3.P-9.1" — so option (a) is the documented intent.

**Recommendation:** At P2.8 entry, confirm with the user that the populated dispositions will be written back into §3.P-9.1 of the source proposal, as the proposal's own filing discipline specifies.

### F-5. `TIER_PROTOCOL_SR.mermaid` references `tier_state_schema.md`

### F-6. Description-length WARN on 7 skills (500-char safety margin)

Seven skills exceed the 500-char description safety margin: `classify-manuscript` (622), `run-phase-1` (962), `run-phase-2` (783), `run-phase-3-stability` (696), `run-phase-3` (960), `run-phase-4` (598), `run-reflection` (613). These are WARNs, not BLOCKERs.

**Context:** The architecture's §3.2 P2.3 closure (r14) notes this as "Optional: shorten run-phase SKILL `description:` YAML strings below 500 chars (release-gate WARN only — not a BLOCKER)." This is already acknowledged.

**Risk:** Low. Over-long descriptions may be truncated in some plugin-discovery surfaces. The descriptions were widened during the v0.8.0 β SKILL rewrites (P2.3) because the new check-profile, MCR, and convergence semantics need to be surfaced for correct skill dispatch.

**Recommendation:** Trim at Phase 5.2 alongside the `plugin.json` description rewrite. Prioritize `run-phase-1` (962 chars) and `run-phase-3` (960 chars) which are nearly double the margin.

### F-7. `audit-package-speed` invocation fails in release-gate

The release-gate's efficiency-config + chain-depth regression gate block (Phase 1.3) reports: `[WARN] audit-package-speed invocation failed (rc=2); gate not evaluated`. The chain-depth check cannot be verified because the calibrator plugin's speed-audit script fails with exit code 2 in this environment.

**Risk:** Medium. Phase 1.3 wired the chain-depth regression gate (`max_chain_depth <= 15`) into `release-gate.sh`, but the gate degrades to a WARN when the calibrator plugin is not reachable. The v0.8.0 release-gate (§3.3 item 2) requires the curated `.plugin-calibrator.json` as authoritative — but the actual chain-depth measurement cannot be confirmed until the calibrator runs successfully.

**Recommendation:** At Phase 5.4 (the full three-axis calibrator probe), ensure the calibrator environment is correctly wired. The WARN-degradation behavior is the correct fail-open design for the authoring substrate, but the Phase 5.4 gate must run in a calibrator-available environment.
