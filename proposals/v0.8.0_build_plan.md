### 1.2 Derived model-assignment rules

From the 17-sample taxonomy (plus the P3.1 partial-land observation), three demand profiles emerge with clear model boundaries:

| Profile | Characteristics | Model | Examples (n) | Cost ratio vs Opus |
|---|---|---|---|---|
| **Mechanical** | grep, string substitution, file rename, count reconciliation, release-gate invocation, zip build | **Haiku 4.5** | P0.1–P0.5 (5) | 1/15 input, 1/15 output |
| **Schema / Script / Doc-alignment** | Additive field-adds, validator extension, migration scripts, contract documentation, fixture authoring, CHANGELOG/README prose, user-decision facilitation with constraint enforcement | **Sonnet 4.6** | P0.1a, P2.1a, P2.1a.1, P2.1b–P2.1d, P2.7, P2.8 (8) | 1/5 input, 1/5 output |
| **Prompt engineering / Governance rewrite** | Agent prompt authoring, multi-section reference rewrites with interlocking contract surfaces, adversarial-register design, semantic-judgment tasks, cross-vocabulary adaptation | **Opus 4.7** | P2.2–P2.6, P3.1 partial (6) | 1/1 (baseline) |

**Decision rule:** A task belongs to Opus 4.7 if it requires the agent to hold multiple interlocking contract surfaces in working memory simultaneously and make semantic judgments about their consistency. If the task's correctness can be verified by a grep or a validator run, it does not need Opus.

## 4. Recommended execution order

### 4.1 Critical path

```
Session A (P3.1 verify) → Session B (P3.2 envelope) → Session D (CHANGELOG + hygiene) → Session E (zip + gate + ship)
```

The critical path runs through Sessions A and B (the two paired-review gates). P2.8 is already closed. Everything else can be resequenced without affecting ship date.

### 4.2 Parallelization opportunities

- **Session C (sk20 refactor + vocab sweep) is independent of Sessions A and B.** It can run in parallel with either, or even before them — the sk20 script and the evaluator vocab sweep do not touch any file that Sessions A/B modify.
- **Phase 4 (verdict cache) is independent of Phase 3.** The cache specification depends on `halo_scope` (landed at P2.2) and `paragraph_hash_map.py` (landed at P2.1c), both of which are already on the wip0 substrate. Phase 4 can run in parallel with Phase 3 Sessions A/B.
- **Session D (CHANGELOG + hygiene) depends on Phases 3 and 4 being closed** — the CHANGELOG must describe them. Session E depends on Session D.

### 4.3 Optimal schedule with parallelization

```
Day 1:  Session A (Opus, P3.1 verify)  ┐
        Session C (Sonnet, P3.3+3.4)   ┤  ← parallel
        Phase 4 (Sonnet, cache)        ┘
                                                                       
Day 2:  Session B (Opus, P3.2 envelope) ─── depends on Session A ─────┐
                                                                       │
Day 3:  Session D (Sonnet, fixture repair + CHANGELOG + hygiene) ──────┤
        Session E (Sonnet, zip + gate + ship) ─── depends on D ────────┘
```

**Minimum calendar: 3 days / 6 sessions** (P2.8 already closed).

### 4.4 Compressed schedule (aggressive)

```
Day 1:  Session A (P3.1 verify) + Session C (parallel: sk20 refactor) + Phase 4 (parallel: cache)
Day 2:  Session B (P3.2 envelope) + Session D + Session E (ship)
```

**Minimum calendar: 2 days / 6 sessions.**

### 4.5 Process risk: paired-review cooldown

The advisor feedback correctly identified that packing Sessions A and B back-to-back is a process risk. Both carry paired-review gates that require sustained semantic judgment. Mitigations:

- **Separate days is preferred.** The optimal schedule (§4.3) puts A and B on different days. This is the recommended path.
- **If same-day is necessary,** insert a minimum 30-minute cooldown between Session A's paired review and Session B's envelope extraction. Session A's Opus portion is read-only verification (lower cognitive load); Session B's Opus portion is multi-file extraction (higher). Starting Session B fresh matters more than starting Session A fresh.
- **Context-window pressure.** A single Opus context window that runs Session A then Session B without clearing accumulates ~130k input tokens of evaluator, SKILL, and PHASE_PROTOCOL context. This is within the 1M window but may degrade output quality on the second review. A fresh session for B is structurally safer.

## 5. Model-selection decision tree (reusable)

For any future task in this plugin's lifecycle, apply this tree:

```
1. Can the task be verified by a grep, a validator exit code, or a file-existence check?
   YES → Haiku 4.5
   NO  → continue

2. Is the task's target fully specified by an existing schema doc, proposal, or diff?
   YES → Sonnet 4.6
   NO  → continue

3. Does the task require holding 2+ interlocking contract surfaces in working memory
   and making semantic judgments about their consistency?
   YES → Opus 4.7
   NO  → Sonnet 4.6 (default for unclassified tasks)
```

**Override rule:** If a Sonnet-assigned task produces output that will be consumed by an Opus-assigned paired review in the same session, keep it at Sonnet — the review will catch errors. If a Sonnet-assigned task has no downstream review gate and is prompt-surface-bearing (i.e., it will be read by an agent at runtime), escalate to Opus.
