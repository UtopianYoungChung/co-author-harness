## 3. Review findings the next session should carry forward

Flags I raised against the eight-proposal package that need attention in the v0.7.4 authoring pass. None of these are rejections; they are design decisions the next session will need to close.

### 3.1 P-1 — `model_used` as a seventh log-row field

The current `SectionStateObject` log row is six fields: `{prev_tier, new_tier, trigger, actor, notes (≤280), timestamp}`. P-1 proposes recording which model produced each row, which adds a seventh field `model_used`. The v0.7.3 schema is not prepared for this addition. Two options for the next session:

- **Option X — Extend the row shape.** Widen to seven fields. Absent-means-null migration for rows predating v0.7.4. Reflector Phase 2f gains a null-tolerant read.
- **Option Y — Push `model_used` into `notes`.** Reserve a `[model=<id>]` prefix in the ≤280-char notes field. No schema change. Slightly less queryable but zero-migration.

The proposal text implies Option X without naming it. The next session should pick one explicitly.

### 3.2 P-2 — hash algorithm and the "non-whitespace line changed" test

Step S-0 ("compute manuscript hash of `manuscript/main.md` against the fingerprint recorded in the prior iteration's consolidated findings") needs a deterministic specification. Propose:

- Hash algorithm: SHA-256 over the manuscript after a canonicalization pass — strip trailing whitespace on every line, normalize line endings to LF, no BOM.
- "Non-whitespace line changed" test: diff the canonicalized manuscript against the prior iteration's canonicalized snapshot; a non-whitespace change is any diff hunk that includes at least one added or removed non-whitespace character.
- Both values live in `reviews/t3_stability_confirmation_<cycle_id>.md` frontmatter so they are inheritable.

Any weaker specification lets line-ending drift or trailing-whitespace drift masquerade as a real change and forces the drop-through to full `run-tier-3`.

### 3.3 P-2 — escalation as an enum trigger

The proposal names the escape-hatch signal `stability_mode_escalation` but does not slot it as an enum trigger. If it is going to appear in `phase_entry_log` (the renamed `tier_entry_log`), it must be a trigger. Proposed slot: **trigger 30 `stability_mode_escalated_to_full_phase3`** (note the phase-named form — see §4).

### 3.4 P-3 — the frontmatter schema is not yet authored

P-3 promises YAML frontmatter carrying "every verdict, counter, and severity-aggregate" but does not specify the schema per artefact family. The next session must author a fixed schema in a new file — proposal: `references/ARTEFACT_FRONTMATTER_SCHEMA.md` — with a validator in `scripts/artefact_frontmatter_validate.py`. Without the fixed schema, P-2's hash-check compares inconsistent surfaces and stability-mode silently diverges round over round.

Schema families needed:

- Evaluator findings frontmatter (severity aggregates, Check 8 Sub-check counters, DND byte-verification result, Coupling E.2 overlay verdict).
- Evaluator deterministic frontmatter (pattern counters from DETERMINISTIC_CHECKS §9a/§9b).
- Reflector-lightweight probe frontmatter (grounding-audit verdict, Phase 2f row-audit result).
- Reflector-full report frontmatter (Phase 1–6 aggregate; Phase 2g recurrence state).
- Planner consolidated-findings frontmatter (round-level aggregation).

### 3.5 P-4 — migration script

`reviews/convergence_log.md` splits into `reviews/convergence_journal.jsonl` (append-only structured) and a frozen `reviews/convergence_log.md` (Trajectory synthesis). Requires `scripts/migrate_convergence_log_v074.py`. Symmetric with `migrate_v060_to_v070.py`. Idempotent. Emits a migration report that the user confirms via frontmatter append to `reviews/classification.md` (established pattern from v0.7.0 migration).

### 3.6 P-5 — subagent-returned verdict authority

When the Evaluator's Step 0a or Step 0.2 dispatches to a subagent, the parent's `AGENT_CONTRACTS.md` entry must state explicitly that **the subagent-returned verdict is authoritative-as-read** — i.e., the parent does not need to re-verify. Otherwise Reflector Phase 2f cannot distinguish parent-read verdicts from subagent-returned ones, and the audit collapses.

New invariant needed in AGENT_CONTRACTS.md:

> **I-SubAgent-1.** When an agent dispatches a bounded-scope audit (Step 0a, Step 0.2, Phase 1 grounding audit on artefact sets > 3 files, full-file manuscript re-reads for ledger bootstrap) via the `Task` tool with an explicit `subagent_type`, the returned verdict is authoritative-as-read. The parent does not re-verify; the parent records the verdict and cites the dispatch envelope as grounding. Reflector Phase 2f treats subagent-returned verdicts as equivalent to parent-read verdicts for audit purposes, provided the dispatch envelope is recorded in the artefact frontmatter.

### 3.7 P-8 — marker coexistence

`[CEILING-LOCK-STABLE]` needs an aggregation rule with `[CONVERGENCE-STABLE]` and `[CONVERGENCE-BORDERLINE-ACCESSIBILITY]`. Proposed rule: if ceiling-lock fires, it is the primary surface and the convergence markers appear as subordinate lines. The existing `[CONVERGENCE-STABLE]` gate on user approval is preserved — ceiling-lock re-orders the *menu*, not the *gate*.

### 3.8 Evidence gate (package-level)

The proposal's §4 explicitly notes P-1, P-2, P-5, P-6 rest on a single-round signal (INF3006Y iter-7). A second-project recurrence observation (INF3001H's next stability pass) would harden the evidence. **Open user decision** — ship v0.7.4 on iter-7-only evidence, or wait? The next session should present this decision explicitly, not silently.

## 4. Execution ordering the next session should propose

The critical ordering constraint: **tier-named surfaces authored in Track A will be renamed immediately afterward in Track B**. Authoring in reverse order (Track A first in tier-named form, Track B afterward) doubles the churn on every new trigger and field introduced by P-1/P-2/P-3/P-7.

Recommended ordering:

1. **Phase 1 — Rename scaffolding (Track B, first half).**
   - Author `scripts/migrate_v073_to_v074_tier_to_phase.py` with idempotent `phase_state.json` generation and a symmetric legacy-read shim.
   - Extend the validator at `scripts/phase_state_validate.py` to accept both naming schemes for one minor version (v0.7.4 reads both; v0.7.5 drops the tier-named read path).
   - Rename `references/TIER_PROTOCOL.md` → `references/PHASE_PROTOCOL.md`; update all §-refs in `CLAUDE.md`, `Ph.D. Research/CLAUDE.md`, and the agent prompts.
   - **Checkpoint:** Planner refuses to advance until the user confirms the migration report via `user_confirmed_migration_report_at: <ISO timestamp>` in `reviews/classification.md`.

2. **Phase 2 — Author Track A against the phase-named surface.**
   - P-1 dispatches under phase-named allocation; trigger 29 named `ph3_iteration_round_manuscript` (was tier-named `t3_iteration_round_manuscript` in the proposal text).
   - P-2's escalation trigger named `stability_mode_escalated_to_full_phase3` (proposed trigger 30).
   - P-3's frontmatter schema uses `phase_*` field names.
   - P-4's `convergence_journal.jsonl` uses `phase` not `tier` in every row.
   - P-7's additive trigger is phase-named from the start.

3. **Phase 3 — Flip the legacy read path to read-only.**
   - v0.7.4 release ships with dual-read active; v0.7.5 RC drops the tier-named read.
   - Existing projects' v0.7.3 artefacts get a `[v0.7.3-READ-ONLY]` banner.

4. **Phase 4 — Ship Tracks A + B as the v0.7.4 release.**
   - Single CHANGELOG entry; single RELEASE_NOTES; two migration scripts (one for the schema rename, one for P-4's convergence-log split).

Reverse-ordering (author Track A in tier-named form, rename afterward) is not recommended and the next session should push back on it if the user proposes it — the churn cost is doubled and the v0.7.4 diff becomes harder to review.

The canonical `zip -r … -x "*/__pycache__/*" "*/__pycache__" "*.pyc" "*/.DS_Store" "*/setup/*"` recipe cleared it. The recipe should be codified into a `scripts/build-release-zip.sh` at v0.7.4 so the exclusion is not a tribal-knowledge step.
5. **v0.7.3 changelog and release-notes claim the release used the full v0.7.3 description.** Since the manifest description was trimmed at the eleventh hour to 402 chars, the RELEASE_NOTES_v0.7.3.md and CHANGELOG.md entries mention the full model-allocation detail that the manifest description no longer carries.
